# KubeAI Kubernetes 组件说明

本文档说明 `infra/k8s` 目录下各 Kubernetes 组件的用途、部署顺序和在 KubeAI 项目中的作用。该目录提供独立 YAML 部署方式，适合按需安装、调试或替代 Helm 一键部署。

## 部署前准备

- 确认可访问 Kubernetes 集群：`kubectl cluster-info`
- 确认当前账号有集群级权限，部分组件会创建 CRD、ClusterRole、ClusterRoleBinding。
- 后端和前端默认调度到带 `kubeai=true` 标签的节点，可执行：`kubectl label node <node-name> kubeai=true`
- 部署前修改 `backend-config.yaml` 中的 `SECRET_KEY`、数据库密码、MinIO 凭证等敏感配置。
- 确认后端、前端镜像已构建或可从镜像仓库拉取。

## 简要部署顺序

### 基础部署

```bash
kubectl apply -f infra/k8s/namespace.yaml
kubectl apply -f infra/k8s/postgresql/
kubectl apply -f infra/k8s/redis/
kubectl apply -f infra/k8s/minio/

kubectl wait --for=condition=ready pod -l app.kubernetes.io/name=postgresql -n kubeai --timeout=120s

kubectl apply -f infra/k8s/backend-config.yaml
kubectl apply -f infra/k8s/backend-rbac.yaml
kubectl apply -f infra/k8s/backend/
kubectl apply -f infra/k8s/frontend/
```

### 可选组件

```bash
kubectl apply -f infra/k8s/mlflow/
kubectl apply -f infra/k8s/labelstudio/
kubectl apply -f infra/k8s/ingress/

kubectl apply -f infra/k8s/volcano/00-namespace.yaml
kubectl apply -f infra/k8s/volcano/volcano.yaml
kubectl wait --for=condition=Established --timeout=60s crd/jobs.batch.volcano.sh crd/queues.scheduling.volcano.sh
kubectl apply -f infra/k8s/volcano/99-default-queue.yaml

kubectl apply -f infra/k8s/kserve/00-namespace.yaml
kubectl apply --server-side -f infra/k8s/kserve/kserve-crd.yaml
kubectl wait --for=condition=Established --timeout=60s crd/inferenceservices.serving.kserve.io crd/servingruntimes.serving.kserve.io crd/clusterservingruntimes.serving.kserve.io
kubectl apply -f infra/k8s/kserve/kserve.yaml
kubectl apply --server-side -f infra/k8s/kserve/kserve-cluster-resources.yaml

kubectl apply -f infra/k8s/keda/00-namespace.yaml
kubectl apply --server-side -f infra/k8s/keda/keda.yaml
kubectl apply -f infra/k8s/jupyterhub/jupyterhub.yaml
kubectl apply -f infra/k8s/harbor/harbor.yaml
kubectl apply -f infra/k8s/monitoring/00-namespace.yaml
kubectl apply -f infra/k8s/prometheus/prometheus.yaml
kubectl apply -f infra/k8s/dcgm-exporter/dcgm-exporter.yaml
```

> `kserve-crd.yaml` 必须先于 `kserve.yaml` 部署，KServe/KEDA 大 CRD 需要使用 server-side apply。Prometheus 和 DCGM Exporter 使用 `monitoring` 命名空间，其他 KubeAI 业务组件主要部署在 `kubeai` 命名空间。

## 组件功能说明

| 组件 | 部署文件 | 在项目中的作用 |
|------|----------|----------------|
| 命名空间 | `namespace.yaml` | 创建 `kubeai` 命名空间，承载平台业务组件。 |
| 后端配置 | `backend-config.yaml` | 提供后端运行所需的 ConfigMap 和 Secret，包括数据库、Redis、MinIO、OIDC、JupyterHub、Harbor 等配置。 |
| 后端权限 | `backend-rbac.yaml` | 为后端创建 ServiceAccount 和集群权限，使后端可以管理租户命名空间、训练任务、推理服务、配额、网络策略等资源。 |
| PostgreSQL | `postgresql/postgresql-secret.yaml`、`postgresql/postgresql.yaml` | 平台主数据库，保存 KubeAI 业务数据；同时初始化 MLflow、Label Studio 可用数据库。 |
| Redis | `redis/redis.yaml` | 后端缓存和会话类能力的基础组件，用于提升接口访问和状态处理效率。 |
| MinIO | `minio/minio.yaml` | 对象存储服务，用于保存模型文件、数据集、实验产物等大文件资源。 |
| Backend | `backend/deployment.yaml`、`backend/service.yaml` | FastAPI 后端，提供平台 API，负责用户、租户、任务、模型、数据集、推理服务等业务逻辑。 |
| Frontend | `frontend/deployment.yaml`、`frontend/service.yaml` | React 前端，提供用户操作界面；Nginx 代理 `/api` 和 WebSocket 请求到后端。 |
| Ingress | `ingress/ingress.yaml` | 对外统一入口，将外部 HTTP 请求路由到前端服务，适合生产或类生产访问方式。 |
| MLflow | `mlflow/mlflow-secret.yaml`、`mlflow/mlflow.yaml` | 实验追踪服务，用于记录训练参数、指标、模型产物和实验历史。 |
| Label Studio | `labelstudio/labelstudio-secret.yaml`、`labelstudio/labelstudio.yaml` | 数据标注服务，用于构建和管理标注任务，支撑训练数据准备流程。 |
| Volcano | `volcano/00-namespace.yaml`、`volcano/volcano.yaml`、`volcano/99-default-queue.yaml` | 批处理和 AI 训练任务调度器，后端通过 Volcano Job 提交分布式训练或资源密集型任务。 |
| KServe | `kserve/00-namespace.yaml`、`kserve/kserve-crd.yaml`、`kserve/kserve.yaml`、`kserve/kserve-cluster-resources.yaml` | 模型推理服务框架，后端通过 InferenceService 管理模型在线部署、版本和访问。 |
| KEDA | `keda/00-namespace.yaml`、`keda/keda.yaml` | 事件驱动自动扩缩容组件，可配合推理服务按负载动态伸缩。 |
| JupyterHub | `jupyterhub/jupyterhub.yaml` | 交互式开发环境，为用户提供 Notebook 工作空间，便于数据探索、调试和模型开发。 |
| Harbor | `harbor/harbor.yaml` | 私有镜像仓库，用于保存训练、推理和开发环境所需镜像。 |
| Prometheus/Grafana | `prometheus/prometheus.yaml` | 平台监控组件，采集 Kubernetes、应用和组件指标，并通过 Grafana 展示。 |
| DCGM Exporter | `dcgm-exporter/dcgm-exporter.yaml` | NVIDIA GPU 指标采集组件，为 GPU 使用率、显存、温度等监控提供数据源。 |
| 监控命名空间 | `monitoring/00-namespace.yaml` | 创建 `monitoring` 命名空间，Prometheus 和 DCGM Exporter 依赖此命名空间。 |
| 镜像拉取脚本 | `pull_all_images.sh` | 汇总拉取部署所需镜像，适合离线部署或提前准备镜像缓存。 |

## 重点组件说明

以下 4 个组件都属于平台级能力，不只是普通业务 Deployment。它们较重的原因主要是会安装 CRD、Webhook、APIService、Controller、Scheduler、RBAC、NetworkPolicy，或持有 Ingress/Gateway/Istio API 相关权限。生产环境重点关注它们是否会改变其他业务的 API 创建链路、调度链路和流量访问链路。

### JupyterHub

内部组件：

- Hub：JupyterHub 核心服务，负责认证、会话、用户 Notebook 生命周期。
- Proxy：公共访问入口，将请求转发到 Hub 或用户 Notebook。
- Single-user Server：每个用户启动的 Notebook Pod。
- User Scheduler：JupyterHub 自带用户 Pod 调度器，仅服务 JupyterHub 用户 Pod。
- Image Puller / Placeholder：提前拉取镜像和预留用户 Pod 容量。
- RBAC、NetworkPolicy、PVC：用于 Hub 创建用户 Pod、限制访问路径、保存 Hub 状态。

为什么较重：它不是一个固定服务，而是会按用户动态创建 Pod，并附带代理、调度器、网络策略、权限和持久化资源。

可能影响其他业务的严重点：

- NetworkPolicy：当前 JupyterHub 清单包含 `hub`、`proxy`、`singleuser` 三个 NetworkPolicy，设计目标是限制 `kubeai` 命名空间内 JupyterHub 相关 Pod 的出入流量。其中“同命名空间”指 NetworkPolicy 实际落入的命名空间；按本项目设计应为 `kubeai`，也就是可能与 `backend`、`frontend`、`postgresql`、`redis`、`minio`、`mlflow`、`labelstudio` 等同处一个命名空间。
- NetworkPolicy 命名空间落点：`jupyterhub.yaml` 中部分 NetworkPolicy 未显式写 `metadata.namespace`，直接 `kubectl apply -f infra/k8s/jupyterhub/jupyterhub.yaml` 时会落到当前 kubectl namespace。生产环境应使用 `kubectl apply -n kubeai -f ...` 或补齐 `metadata.namespace: kubeai`，否则可能把策略装到错误命名空间。
- NetworkPolicy 选择范围：这些策略的 `podSelector` 只匹配 `app=jupyterhub`、`component=hub/proxy/singleuser-server` 的 Pod，不会直接选中 `backend`、`frontend`、`postgresql` 等普通 KubeAI 组件。但策略的 `namespaceSelector` 允许访问带 `kubeai.io/tenant-namespace=true` 标签的租户命名空间；租户命名空间标签要谨慎使用，避免把不该暴露给 Notebook 的命名空间纳入访问范围。
- Service/NodePort/Ingress：`proxy-public` 暴露 JupyterHub 入口，生产环境如果与已有 Ingress、网关域名或 NodePort 规划冲突，会影响访问路由。
- RBAC 权限边界：Hub 需要创建和管理用户 Pod、Service、Secret、PVC 等资源；如果权限放得过大，可能误操作同命名空间其他业务资源。
- 调度逻辑：User Scheduler 不替代 `default-scheduler`，通常不影响其他业务 Pod；但如果其他业务误用了 JupyterHub 的 `schedulerName` 或共享了相同节点标签，调度结果会被改变。

生产环境注意事项：

- 建议独立命名空间或至少独立节点池部署，不要和核心业务服务混放在同一命名空间。
- 上线前逐条审查 NetworkPolicy，确认其实际安装命名空间、`podSelector` 和 `namespaceSelector` 符合预期。
- 明确 JupyterHub 入口使用 Ingress、Gateway 还是 NodePort，避免和现有入口控制器重复接管同一域名或端口。
- 限制 Hub ServiceAccount 权限范围，避免具备管理非 Notebook 业务资源的能力。

### KEDA

内部组件：

- KEDA Operator：监听 ScaledObject、ScaledJob，并创建或维护 HPA。
- KEDA Metrics Server：向 Kubernetes 注册 `external.metrics.k8s.io` 外部指标 API。
- Admission Webhook：校验 KEDA 自身 CRD 资源。
- CRD：ScaledObject、ScaledJob、TriggerAuthentication、ClusterTriggerAuthentication 等。
- APIService、RBAC：把外部指标接入 Kubernetes HPA 链路。

为什么较重：KEDA 接入的是 Kubernetes 自动扩缩容控制链路，会注册集群级 APIService，并可能接管业务 Deployment 的 HPA。

可能影响其他业务的严重点：

- APIService 冲突：`external.metrics.k8s.io` 是集群级 API，同一集群通常只能有一个提供方。如果已有外部指标适配器，KEDA 可能覆盖或冲突。
- HPA 行为变化：KEDA 会为 ScaledObject 创建 HPA。如果目标 Deployment 已有手工 HPA 或被其他平台管理的 HPA，会出现重复扩缩容控制。
- 指标服务故障影响：如果 KEDA Metrics Server 不可用，集群内所有依赖 `external.metrics.k8s.io` 的 HPA 都可能无法取数；CPU/内存 HPA 不受影响。
- Webhook 范围：KEDA Webhook 主要校验 `keda.sh` 资源，不拦截普通 Pod、Deployment、Service，一般不会影响其他业务对象创建。

生产环境注意事项：

- 部署前检查：`kubectl get apiservice | grep external.metrics`，确认是否已有外部指标适配器。
- 同一个 Deployment 不要同时由 KEDA ScaledObject、手工 HPA 和其他弹性平台共同管理。
- 对关键业务谨慎启用 scale-to-zero，避免服务被缩到 0 后影响调用方预期。
- 监控 `keda-operator` 和 `keda-operator-metrics-apiserver`，它们故障会影响外部指标扩缩容。

### KServe

内部组件：

- KServe CRD：InferenceService、ServingRuntime、ClusterServingRuntime、InferenceGraph、TrainedModel 等。
- KServe Controller Manager：监听 InferenceService，当前配置的默认部署模式为 `Standard`，即生成底层 Deployment、Service、Ingress 等标准 Kubernetes 资源。
- Mutating / Validating Webhook：为 KServe 资源默认化、校验，并对推理 Pod 做必要注入。
- Storage Initializer：模型服务启动前初始化模型文件。
- cert-manager 相关资源：用于 Webhook TLS 证书签发。
- Ingress/Gateway 配置：当前 `kserve.yaml` 的 `inferenceservice-config` 中 `defaultDeploymentMode` 为 `Standard`，`disableIngressCreation` 为 `false`，`ingressClassName` 为 `istio`，并引用 `kserve/kserve-ingress-gateway`、`knative-serving/knative-ingress-gateway`、`knative-serving/knative-local-gateway` 等网关名称。
- Istio/Knative 相关权限：当前清单没有部署 Istio 或 Knative 组件本体，但 KServe ClusterRole 包含 `networking.istio.io` 的 `virtualservices` 权限、`gateway.networking.k8s.io` 权限，以及 `serving.knative.dev` 相关权限。这是 KServe 控制器兼容多种部署模式所需的权限面。

为什么较重：KServe 是模型服务控制平面，会扩展 Kubernetes API，并可能接管推理服务的路由、灰度、自动伸缩和 Pod 注入链路。

当前清单的严重影响点：

- CRD 版本冲突：同一集群如果已有 KServe，重复安装不同版本 CRD 可能影响已有 InferenceService。
- Webhook 故障：KServe Webhook 证书过期或 Service 不可达，会影响 KServe 资源创建或更新；普通业务 Deployment 通常不受影响。
- Pod Mutator：KServe Pod mutator 通过标签选择器限定到 KServe 推理 Pod；普通 Pod 通常不会被处理，但其他 Webhook 如果也修改推理 Pod，可能产生注入顺序或字段冲突。
- cert-manager 依赖：缺少 cert-manager 会导致 KServe Webhook 证书不可用，从而影响 KServe 控制面。
- IngressClass 影响：当前配置写死 `ingressClassName: istio`。如果集群不存在名为 `istio` 的 IngressClass/入口控制器，KServe 创建出的推理 Ingress 可能无人接管，推理服务外部访问不可用；如果集群已有 Istio Ingress，则推理流量会交给 Istio 入口链路处理。
- 网关名称影响：当前配置引用 `kserve/kserve-ingress-gateway` 和 `knative-serving/...` 网关名称，但本目录没有部署这些网关资源。生产环境需要确认这些 Gateway/Service 是否已存在；不存在时，KServe 控制面可能正常，但推理访问链路不完整。
- VirtualService 权限影响：清单授予 KServe 管理 `networking.istio.io/virtualservices` 的集群权限。如果集群已有 Istio 且 KServe 使用该入口链路，KServe 创建或更新的 VirtualService 可能影响同 host 下的推理流量路由；不会自动改写普通业务 VirtualService，除非 host 或资源命名规划发生冲突。
- Knative 权限影响：清单授予 `serving.knative.dev` 相关权限，但当前默认部署模式是 `Standard`，不会因为安装该 YAML 就部署 Knative 或自动接管其他业务的 Knative Service。

生产环境注意事项：

- 先确认集群是否有 Istio IngressClass、相关 Gateway 和 Gateway Service；没有就需要调整 KServe ingress 配置或补齐入口资源。
- 不要把 KServe 与其他平台的 KServe 安装混用；同一集群建议只保留一套 KServe CRD 和 Controller。
- KServe CRD 升级前先确认现有 InferenceService 版本兼容，避免 CRD schema 改动导致老资源不可更新。
- 推理入口域名、Ingress、Gateway、VirtualService 必须统一规划，避免和业务系统域名、路径规则冲突。

### Volcano

内部组件：

- Volcano Scheduler：独立调度器，只调度 `schedulerName: volcano` 的 Pod。
- Volcano Controller：管理 Job、Queue、PodGroup 等 Volcano 资源。
- Admission Webhook：校验和默认化 Volcano CRD 资源。
- CRD：Job、Queue、PodGroup、CronJob、JobFlow、HyperNode 等。
- Queue / PodGroup：提供队列、Gang Scheduling、资源组调度能力。
- RBAC、Service、初始化 Job：支撑调度器、控制器和 Webhook 运行。

为什么较重：Volcano 是独立批处理调度体系，会新增 CRD、调度器、控制器、队列模型和 Admission Webhook。

可能影响其他业务的严重点：

- 调度器边界：Volcano 不替代 `default-scheduler`，普通业务 Pod 不会被 Volcano 调度；但任何业务只要设置了 `schedulerName: volcano`，调度逻辑就会进入 Volcano 队列和 PodGroup 规则。
- 队列策略影响：如果多个团队共用 Volcano Queue，队列配额、优先级、抢占策略可能影响其他训练或批处理任务是否能被调度。
- PriorityClass：Volcano 控制面组件可能使用较高优先级，极端情况下可能影响低优先级 Pod 的稳定性；应部署到平台组件节点。
- Webhook 范围：Volcano Webhook 主要处理 Volcano CRD，不拦截普通 Deployment、Service、原生 Job；但 Volcano CRD 创建会依赖 Webhook 可用性。
- CRD 版本冲突：集群中已有 Volcano 时，重复安装不同版本可能导致 Queue、Job、PodGroup schema 不兼容。

生产环境注意事项：

- 明确只有 KubeAI 训练任务使用 `schedulerName: volcano`，其他业务不要误配置。
- 生产环境要预先设计 Queue、PriorityClass、租户配额和抢占策略。
- 如果集群已有 Volcano，优先复用现有安装，不要重复安装另一套 CRD 和控制器。
- 升级或卸载前确认没有运行中的 Volcano Job，避免训练任务中断或状态残留。

### 严重冲突风险总览

| 冲突类型 | 涉及组件 | 严重影响 |
|----------|----------|----------|
| CRD 版本冲突 | KServe、KEDA、Volcano | 重复安装不同版本可能导致已有自定义资源无法创建、更新或被错误解析。 |
| APIService 冲突 | KEDA | `external.metrics.k8s.io` 被覆盖或故障，会影响所有依赖外部指标的 HPA。 |
| Webhook 故障 | KServe、KEDA、Volcano | 对应资源创建、更新可能失败或延迟；KServe 证书问题尤其常见。 |
| 调度逻辑变化 | Volcano、JupyterHub | 误用 `schedulerName: volcano` 或 JupyterHub User Scheduler 会改变 Pod 调度路径。 |
| Istio/Ingress 接入 | KServe | 当前 KServe 配置使用 `ingressClassName: istio` 并引用 Gateway 名称；入口资源不存在会导致推理访问不可用，host 规划冲突会影响推理路由。 |
| 入口路由冲突 | KServe、JupyterHub | Ingress、Gateway、VirtualService 域名重复可能导致外部访问路由错乱。 |
| HPA 控制冲突 | KEDA | 同一 Deployment 被多个 HPA/ScaledObject/弹性平台同时管理，会导致副本数反复震荡。 |

## 访问方式

集群内组件通过 Service 名称访问，例如后端为 `backend.kubeai.svc.cluster.local:8000`，前端为 `frontend.kubeai.svc.cluster.local:80`。

本地调试可使用端口转发：

```bash
kubectl port-forward -n kubeai svc/frontend 3000:80
kubectl port-forward -n kubeai svc/backend 8000:8000
kubectl port-forward -n kubeai svc/minio 9001:9001
kubectl port-forward -n kubeai svc/mlflow 5000:5000
kubectl port-forward -n kubeai svc/labelstudio 8080:8080
```

所有 KubeAI 组件 Service 默认 `ClusterIP`，生产环境通过 Ingress 暴露，开发调试使用 `kubectl port-forward`。

## 依赖关系

- 最小可运行平台：`namespace`、`postgresql`、`redis`、`minio`、`backend-config`、`backend-rbac`、`backend`、`frontend`。
- 训练任务能力：需要部署 `volcano`，后端需具备对应 RBAC 权限。
- 在线推理能力：需要部署 `kserve`，如需弹性伸缩再部署 `keda`。
- 实验管理能力：部署 `mlflow` 后，在后端配置中启用 `MLFLOW_ENABLED` 并确认 `MLFLOW_TRACKING_URI`。
- 数据标注能力：部署 `labelstudio` 后，在后端配置中设置 `LABEL_STUDIO_URL` 和 `LABEL_STUDIO_API_TOKEN`。
- 开发环境能力：部署 `jupyterhub` 后，在后端配置中设置 JupyterHub API 和 Token。
- GPU 监控能力：需要 GPU 节点、NVIDIA 驱动和 `dcgm-exporter`，并配合 Prometheus 采集。
